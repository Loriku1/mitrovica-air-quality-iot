# F1 Project Journal – Mitrovica Air Quality IoT

**Project:** Mitrovica Air Quality – IoT Platform  
**Phase:** F1 – Architecture and Initial Implementation  
**Date:** 13 November 2026

## 1. Project Overview

The project aims to develop an IoT-based air quality monitoring platform for Mitrovica. The system will collect PM2.5 and PM10 measurements from distributed sensors, process incoming data, store historical measurements, and generate alerts when pollution thresholds are exceeded.

The main engineering challenge is to support 1,000 sensors sending measurements every five seconds, resulting in approximately 200 messages per second, while ensuring reliable ingestion and timely alert delivery.

## 2. Architecture and Design Decisions

The system was designed using a microservices architecture with three core services:

- **Ingestion Service:** Responsible for receiving and validating sensor measurements.
- **Storage Service:** Responsible for storing measurements and providing historical data and aggregates.
- **Alert Service:** Responsible for evaluating pollution thresholds and managing alerts.

Each service has independent data ownership. Synchronous HTTP communication is planned for API interactions, while RabbitMQ is selected for asynchronous message processing.

Three Architecture Decision Records (ADRs) were documented:

1. Microservices architecture and data ownership.
2. RabbitMQ for asynchronous communication.
3. PostgreSQL with TimescaleDB for time-series storage.

## 3. Service Implementation

Initial runnable skeletons were created for all three services using Node.js, TypeScript, and Express.

Each service exposes a `/health` endpoint:

- Ingestion Service – port 3101
- Storage Service – port 3102
- Alert Service – port 3103

TypeScript type checking was configured, and development scripts were added to run the services individually or together.

## 4. SLOs and Risk Analysis

The following initial targets were documented:

- Alert delivery latency: p95 ≤ 10 seconds.
- Ingestion throughput: 200 messages per second for 30 minutes, with zero loss of accepted measurements.
- API availability: ≥ 99.5% over 30 days.
- Raw measurement retention: 7 days.
- One-minute aggregate retention: 90 days.

A risk assessment was also completed, identifying seven risks, including message loss, processing delays, sensor failures, database failures, duplicate processing, and unauthorized access.

## 5. Current Implementation Status

The repository currently contains the initial service skeletons, project documentation, architecture diagrams, ADRs, SLO definitions, risk analysis, and OpenAPI contracts.

RabbitMQ, TimescaleDB, transactional outbox, Kubernetes, monitoring, and distributed tracing remain planned implementation components. They are documented as architectural decisions and future work, not as completed functionality.

## 6. Next Steps

The next development phase will focus on:

- Implementing measurement ingestion and validation.
- Integrating PostgreSQL and TimescaleDB.
- Introducing RabbitMQ and reliable asynchronous processing.
- Implementing alert evaluation.
- Adding Docker and Kubernetes deployment.
- Integrating Prometheus, Grafana, and OpenTelemetry.
- Testing throughput, reliability, and alert latency against the defined SLOs.
